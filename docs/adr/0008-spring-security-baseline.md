# ADR-0008: JWT보다 먼저 Spring Security 요청 경계를 구축한다

- 상태: 승인
- 날짜: 2026-09-04

## 배경

로그인과 JWT부터 구현하면 공개 경로, 보호 경로, 401과 403의 의미, 오류 응답 위치가 한꺼번에 섞인다. 특히 Spring Security 필터에서 발생한 예외는 Spring MVC의 전역 예외 처리기에 도달하지 않으므로 기존 공통 오류 계약만으로는 일관된 응답을 만들 수 없다.

또한 Spring Boot가 임시 기본 사용자를 자동 생성하거나 폼 로그인으로 리다이렉트하면 API 클라이언트가 예상하지 못한 동작을 하게 된다.

## 결정

- Spring Security Filter Chain을 먼저 도입한다.
- 애플리케이션 Health와 Actuator Health만 공개한다.
- 다른 Actuator 엔드포인트는 `ADMIN`, 그 외 요청은 인증을 요구한다.
- 세션 정책은 stateless로 설정한다.
- 폼 로그인, HTTP Basic, 로그아웃, 요청 캐시는 비활성화한다.
- 계정 구현 전에는 비어 있는 `UserDetailsService`를 제공해 임시 기본 사용자를 만들지 않는다.
- 401은 `AuthenticationEntryPoint`, 403은 `AccessDeniedHandler`에서 처리한다.
- MVC 오류와 보안 오류는 같은 `ApiProblemDetailFactory`를 사용한다.
- 현재의 명시적 Bearer Token 계획을 전제로 CSRF를 비활성화하되, 쿠키 기반 인증이나 교차 출처 Embed 정책이 도입되기 전에 재검토한다.
- CORS는 지금 전체 허용하지 않고 등록 제휴사 Origin 정책이 생길 때 구현한다.

## 이유

- JWT 세부 구현과 무관하게 보호할 URL과 권한 정책을 먼저 테스트할 수 있다.
- 인증 실패와 권한 부족을 각각 HTTP 401과 403으로 명확히 표현한다.
- API가 HTML 로그인 페이지로 리다이렉트되거나 세션 쿠키를 생성하는 일을 막는다.
- 필터 계층과 MVC 계층의 오류 응답 계약을 하나로 유지한다.
- 이후 JWT 필터는 인증 객체를 제공하는 책임에 집중하고 기존 인가 규칙을 재사용할 수 있다.

## 대안

### JWT 발급과 필터를 한 번에 구현

빠르게 로그인처럼 보이는 흐름을 만들 수 있지만 계정 모델, 비밀번호 저장, 토큰 키, 갱신 정책, URL 인가 규칙을 동시에 검증해야 한다. 실패 원인을 분리하기 어렵기 때문에 채택하지 않았다.

### 모든 요청을 임시 공개

기능 개발은 편하지만 새 API가 실수로 공개된 채 남을 수 있다. 기본값을 `authenticated`로 두고 공개 경로만 명시하는 방식이 더 안전하다.

### Spring Boot 기본 사용자와 HTTP Basic 사용

빠른 수동 확인에는 편하지만 실제 목표인 API 인증 모델과 다르고 임시 비밀번호가 실행 로그에 나타날 수 있다. 과도기에도 의도하지 않은 인증 방식을 노출하지 않기로 했다.

### Security Filter Chain을 무시해 Health 공개

요청이 보안 필터를 완전히 우회한다. 공개 경로에도 보안 헤더를 유지하기 위해 `permitAll`을 선택했다.

## 결과

### 장점

- 보안 기본값이 공개가 아닌 인증 필요 상태가 된다.
- 401·403이 공통 RFC 9457 응답으로 제공된다.
- 공개 Health에도 기본 보안 헤더가 적용된다.
- JWT와 DB 계정 구현을 작은 후속 단계로 분리할 수 있다.

### 비용

- 로그인 구현 전에는 Health 외 실제 API에 접근할 인증 수단이 없다.
- 필터 계층용 오류 처리 구성요소가 추가된다.
- 쿠키와 Embed 정책이 확정되면 CSRF·CORS 결정을 다시 검토해야 한다.

## 검증 방법

- 익명 사용자의 공개 Health 접근이 200인지 확인한다.
- 익명 사용자의 보호 API 접근이 401 Problem Details인지 확인한다.
- 인증된 일반 사용자의 관리자 경로 접근이 403 Problem Details인지 확인한다.
- 인증된 요청의 MVC 404가 기존 공통 오류 계약을 유지하는지 확인한다.
- 응답에 리다이렉트와 세션 쿠키가 없는지 확인한다.
- 실제 서버에서 공개·보호 경로와 보안 헤더를 확인한다.

## 재검토 조건

- DB 기반 회원과 역할을 도입할 때
- JWT Access·Refresh Token 정책을 확정할 때
- Refresh Token을 쿠키로 전달할 때
- Embed SDK의 허용 Origin과 브라우저 저장 방식을 확정할 때
- 운영용 Actuator 접근을 별도 포트나 내부 네트워크로 분리할 때
