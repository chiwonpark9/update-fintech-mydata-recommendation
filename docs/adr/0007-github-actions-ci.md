# ADR-0007: GitHub Actions에서 백엔드와 프론트엔드 CI를 병렬 실행한다

- 상태: 승인
- 날짜: 2026-09-04

## 배경

로컬에서 테스트한 코드도 운영체제, 설치 상태, 환경 변수의 영향으로 다른 컴퓨터에서 실패할 수 있다. 인증, 마이데이터, 추천 기능이 추가되면 변경 범위가 넓어지므로 `main`에 반영하기 전에 백엔드와 프론트엔드의 회귀를 자동으로 발견할 장치가 필요하다.

## 결정

- GitHub Actions를 CI 실행 환경으로 사용한다.
- `main` push, `main` 대상 Pull Request, 수동 실행을 지원한다.
- 백엔드와 프론트엔드를 독립 job으로 나누어 병렬 실행한다.
- 백엔드는 Java 17과 Gradle Wrapper로 `clean test bootJar`를 실행한다.
- 프론트엔드는 Node.js 22에서 `npm ci`, 테스트, 코드 검사, 빌드를 실행한다.
- MySQL 통합 테스트는 별도 공유 DB가 아니라 Testcontainers를 사용한다.
- 의존성 캐시를 사용하되 테스트와 빌드는 매번 수행한다.
- `GITHUB_TOKEN`은 `contents: read` 최소 권한만 사용한다.
- 외부 액션은 공식 릴리스에서 확인한 전체 커밋 SHA로 고정한다.
- 같은 브랜치의 오래된 실행은 취소하고 최신 커밋을 검사한다.

## 이유

- GitHub 저장소와 가까운 위치에서 Pull Request 상태 검사를 제공할 수 있다.
- 독립 job은 실행 시간을 줄이고 실패 영역을 빠르게 구분하게 한다.
- 로컬과 같은 Wrapper와 npm scripts를 사용하면 CI 전용 로직을 줄일 수 있다.
- Testcontainers는 MySQL 버전과 Flyway 마이그레이션을 포함한 재현 가능한 테스트 환경을 제공한다.
- 최소 권한과 SHA 고정은 workflow 공급망과 토큰 오용 위험을 줄인다.

## 대안

### 백엔드와 프론트엔드를 하나의 job에서 순서대로 실행

설정은 짧지만 앞 단계가 실패하면 뒤 단계 결과를 얻을 수 없고 전체 시간이 길어진다.

### CI용 MySQL service container를 workflow에 직접 선언

모든 테스트가 하나의 DB를 공유해 상태 격리가 약해지고 로컬 통합 테스트와 구성이 달라진다. 현재는 테스트 클래스가 필요한 MySQL을 직접 관리하는 Testcontainers를 유지한다.

### 액션의 major 태그만 사용

업데이트가 자동 반영되는 장점이 있지만 태그가 이동할 수 있다. 이 프로젝트는 재현성과 공급망 통제를 우선해 전체 SHA를 사용하고 버전 갱신을 명시적으로 검토한다.

### 로컬 Git hook만 사용

빠른 피드백에는 유용하지만 사용자가 우회할 수 있고 GitHub의 병합 기준으로 사용할 수 없다. 필요해질 때 CI를 보완하는 용도로 검토한다.

## 결과

### 장점

- 모든 `main` 변경에 동일한 자동 검증을 적용한다.
- 백엔드와 프론트엔드 실패를 독립적으로 확인한다.
- CI에 실제 DB 비밀번호나 장기 실행 테스트 DB가 필요하지 않다.
- 실행 결과와 로그가 GitHub 커밋에 연결되어 포트폴리오 증거가 된다.

### 비용

- 최초 실행과 캐시가 비어 있는 실행은 의존성 다운로드 시간이 필요하다.
- 액션 SHA를 고정했으므로 새 버전을 주기적으로 확인해야 한다.
- GitHub 서비스나 패키지 저장소 장애가 CI 결과에 영향을 줄 수 있다.

## 검증 방법

- workflow YAML 문법을 로컬에서 확인한다.
- 로컬에서 백엔드 전체 테스트와 JAR 빌드를 실행한다.
- 로컬에서 프론트엔드 의존성 재현 설치, 테스트, 코드 검사, 빌드를 실행한다.
- `main`에 workflow를 올린 뒤 GitHub Actions의 두 job 성공을 확인한다.
- README CI 배지가 성공 상태를 표시하는지 확인한다.

## 재검토 조건

- 프로젝트가 여러 Gradle 모듈 또는 프론트엔드 패키지로 분리될 때
- CI 실행 시간이 개발 피드백을 방해할 정도로 길어질 때
- Pull Request 협업을 시작해 branch protection이 필요할 때
- AWS 배포 workflow와 환경별 승인 정책을 도입할 때
