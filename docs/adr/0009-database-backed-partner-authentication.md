# ADR-0009: 제휴사 키와 이메일을 함께 검증하는 DB 인증 기반을 사용한다

- 상태: 승인
- 날짜: 2026-09-04

## 배경

서비스는 여러 제휴사 홈페이지에 삽입되는 B2B2C 구조를 목표로 한다. 이메일만 전역 로그인 식별자로 사용하면 같은 고객이 여러 제휴사에 가입했을 때 계정과 데이터 범위가 섞일 수 있다. JWT를 먼저 발급하더라도 신원의 원본과 제휴사 경계가 명확하지 않으면 토큰의 `sub`와 권한을 신뢰할 수 없다.

비밀번호는 복호화 가능한 값이나 평문으로 저장해서는 안 되며, 회원이 없는 경우와 비밀번호가 틀린 경우의 차이도 외부에 노출하지 않아야 한다.

## 결정

- MySQL을 제휴사, 회원, 역할의 원본 저장소로 사용한다.
- `partners`, `members`, `member_roles`를 Flyway V2에서 생성한다.
- 회원 유일성은 `(partner_id, email)`로 정의한다.
- 로그인 입력은 `partnerKey + email + password`로 구성한다.
- 제휴사 키를 포함하는 전용 `Authentication` 토큰을 사용한다.
- 전용 `AuthenticationProvider`가 Spring JDBC 조회와 비밀번호 검증을 수행한다.
- `ProviderManager`를 애플리케이션의 `AuthenticationManager`로 제공한다.
- `DelegatingPasswordEncoder`를 사용하고 현재 신규 해시는 BCrypt로 생성한다.
- 인증 결과의 Principal에는 회원·제휴사 식별 정보만 포함하고 비밀번호는 포함하지 않는다.
- 존재하지 않는 회원도 dummy BCrypt 해시와 비교해 큰 시간 차이를 줄인다.
- 계정 없음, 비밀번호 불일치, 비활성 상태는 같은 인증 실패로 처리한다.
- 운영 마이그레이션에는 기본 계정이나 샘플 비밀번호를 넣지 않는다.

## 이유

- 인증 순간부터 제휴사 범위를 조건으로 사용해 교차 제휴사 계정 혼동을 줄인다.
- 비밀번호 확인과 권한 생성을 Spring Security의 Provider 구조 안에 캡슐화한다.
- Spring JDBC를 사용하면 인증 쿼리와 실행 계획을 직접 확인할 수 있고, 이후 MySQL 성능 학습에도 연결된다.
- BCrypt의 salt와 적응형 비용으로 평문 및 단순 고속 해시보다 무차별 대입 공격 비용을 높인다.
- 알고리즘 식별자 형식은 향후 비밀번호 해시 정책 변경을 지원한다.
- 일반적인 실패 응답과 dummy 비교는 계정 존재 여부 노출 위험을 줄인다.

## 대안

### 이메일을 전역 유일 키로 사용

구현은 단순하지만 제휴사마다 독립된 사용자와 동의 상태를 표현하기 어렵다. 현재 제품의 B2B2C 경계와 맞지 않아 채택하지 않았다.

### `partnerKey:email` 문자열을 표준 username에 결합

기본 `DaoAuthenticationProvider`를 재사용하기 쉽지만 문자열 조합 규칙이 여러 계층으로 퍼지고 제휴사 정보를 별도 타입으로 다루기 어렵다. 전용 토큰과 Provider가 의도를 더 명확히 드러낸다고 판단했다.

### JPA로 회원 엔티티 구현

연관관계 매핑은 편리하지만 현재 프로젝트는 Spring JDBC를 기준으로 시작했다. 인증 쿼리를 명시적으로 관리하고 추후 인덱스·실행 계획을 직접 학습하기 위해 JDBC를 유지한다.

### BCrypt 해시만 접두어 없이 저장

현재 검증은 가능하지만 향후 다른 알고리즘과 비용 정책으로 이동할 때 값을 구분하기 어렵다. `DelegatingPasswordEncoder`의 `{id}encodedPassword` 형식을 선택했다.

### 마이그레이션에 데모 계정 삽입

실행 직후 확인은 쉽지만 고정 비밀번호가 운영 환경에도 함께 적용될 위험이 있다. 운영 스키마와 합성 데모 데이터 생성을 분리한다.

## 결과

### 장점

- JWT 발급 전 신원과 제휴사 범위를 DB에서 검증할 수 있다.
- 회원 상태와 제휴사 상태를 한 인증 쿼리에서 확인한다.
- 역할이 `ROLE_CUSTOMER`, `ROLE_PARTNER_ADMIN`, `ROLE_PLATFORM_ADMIN`으로 변환된다.
- 원문 비밀번호가 DB, Principal, 인증 성공 결과에 남지 않는다.
- 인증 실패가 외부에서 구분되기 어려운 형태로 통일된다.

### 비용

- 표준 username/password보다 전용 토큰과 Provider 코드가 추가된다.
- 로그인할 때 DB 조회와 의도적으로 느린 비밀번호 비교 비용이 발생한다.
- 로그인 API가 생기기 전까지 이 인증 기반은 HTTP에서 직접 사용할 수 없다.
- tenant 식별 방식과 Embed 초기화 흐름이 확정되면 partner key 전달 방식을 다시 검토해야 한다.

## 검증 방법

- 실제 MySQL 8.4에서 Flyway V2를 적용한다.
- 정상 제휴사·회원·비밀번호로 Authentication을 생성한다.
- 다른 제휴사, 잘못된 비밀번호, 잠긴 회원, 중지된 제휴사를 거부한다.
- 같은 제휴사 내 이메일 중복과 잘못된 상태·역할을 DB 제약으로 차단한다.
- 같은 비밀번호의 두 BCrypt 해시가 다르고 모두 검증되는지 확인한다.
- 인증 후 credentials가 제거되고 Principal에 해시가 없는지 확인한다.
- 임시 기본 사용자 없이 DB AuthenticationProvider가 등록되는지 확인한다.

## 재검토 조건

- 제휴사 외에 통합 소비자 계정이 필요해질 때
- 소셜 로그인이나 기업 SSO를 추가할 때
- 사용자 수와 로그인 트래픽이 증가해 인증 쿼리 성능 측정이 필요할 때
- AWS 인스턴스 유형이 정해져 BCrypt 비용 값을 측정할 때
- 회원 생성·비밀번호 재설정·계정 복구 정책을 설계할 때
