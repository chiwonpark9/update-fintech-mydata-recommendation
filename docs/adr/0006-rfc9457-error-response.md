# ADR-0006: API 오류 응답은 RFC 9457 Problem Details를 확장한다

- 상태: 승인
- 날짜: 2026-09-04

## 배경

로그인 사용자 정보, 카드 추천, AI 상담 모듈은 서로 다른 제휴사 화면에서도 같은 API를 사용하게 된다. 컨트롤러마다 오류 형식이 다르면 클라이언트가 HTTP 상태와 메시지 문자열을 임의로 해석하게 되고, 내부 예외 내용을 그대로 반환하면 보안 정보가 노출될 수 있다.

## 결정

- Spring MVC의 RFC 9457 `ProblemDetail`을 공통 오류 본문으로 사용한다.
- 표준 필드에 `code`, `timestamp`, `fieldErrors`를 추가한다.
- `@RestControllerAdvice`와 `ResponseEntityExceptionHandler`로 MVC 예외 처리를 중앙화한다.
- 클라이언트는 `detail` 문장이 아니라 안정적인 `code`를 기준으로 분기한다.
- 예상하지 못한 예외는 서버 로그에 기록하고 외부에는 일반적인 500 설명만 반환한다.
- 검증 실패 시 필드 이름과 안전한 사유만 반환하며 거부된 입력 값은 포함하지 않는다.

## 이유

- 공개 표준 필드를 사용하면 오류 구조를 새로 정의하고 설명하는 비용을 줄일 수 있다.
- 서비스 오류 코드는 UI 처리와 제휴사 연동 계약을 안정적으로 유지한다.
- 필드 오류 목록은 입력 화면이 정확한 위치에 안내를 표시할 수 있게 한다.
- 중앙 처리로 새로운 도메인이 생겨도 보안 원칙과 응답 형식을 재사용할 수 있다.
- 내부 예외와 외부 표현을 분리해 구현 정보 노출을 줄인다.

## 대안

### 자체 JSON 형식만 사용

구현은 단순하지만 표준 HTTP 오류 도구와 문서를 활용하기 어렵고 프로젝트 전용 규약이 커진다.

### Spring 기본 오류 응답을 그대로 사용

초기 코드는 적지만 도메인별 안정적인 서비스 코드와 필드별 검증 계약을 제공하기 어렵다.

### 예외 메시지를 그대로 반환

개발 중에는 편리하지만 SQL, 경로, 라이브러리 정보나 개인정보가 외부에 노출될 위험이 있어 사용하지 않는다.

## 결과

### 장점

- 400, 404, 405, 415, 500 오류가 같은 구조를 가진다.
- 프론트엔드가 `code`와 `fieldErrors`로 일관되게 처리할 수 있다.
- 예상 오류와 예상 밖 오류를 분리해 로깅과 외부 노출 정책을 다르게 적용한다.
- 향후 인증과 추천 도메인 오류 코드를 같은 규칙으로 확장할 수 있다.

### 비용

- 오류 코드를 추가할 때 코드, 테스트, 문서를 함께 관리해야 한다.
- 사용자 문구의 다국어 처리는 아직 구현하지 않았다.
- 요청 추적 ID는 관측성 구성을 도입할 때 추가해야 한다.

## 검증 결과

- DTO와 쿼리 파라미터 검증 오류의 필드 목록을 확인했다.
- 잘못된 JSON에서 파서 내부 정보가 노출되지 않음을 확인했다.
- 404, 405, 415와 업무 예외가 지정된 코드로 반환됨을 확인했다.
- 예상 밖 예외 메시지가 500 응답에서 가려짐을 확인했다.
- 실제 실행 서버에서 404, 405, 정상 200 응답을 비교했다.

## 재검토 조건

- 제휴사와 오류 계약 버전 관리가 필요해질 때
- 다국어 메시지와 오류 문서 URL을 제공할 때
- 분산 추적 ID를 모든 응답과 로그에 연결할 때
